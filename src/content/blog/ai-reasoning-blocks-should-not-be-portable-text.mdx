# AI Reasoning Blocks Should Not Be Portable Text

Most application developers treat an AI response as a collection of content blocks.

Text can be stored.

Tool calls can be replayed.

Images can be moved.

Conversation history can be rebuilt before the next request.

That mental model becomes dangerous when one of those blocks contains the model's intermediate reasoning.

A reasoning block may look like text in JSON, but it should behave more like signed session state:

```txt
valid for this conversation
valid for this model relationship
valid for this organization
invalid when its history is rewritten
```

The distinction matters because portable reasoning can be copied into a different conversation, sent through a weaker model, or moved across accounts in an attempt to reveal or reuse information that was meant to remain protected.

The safer design principle is simple:

```txt
Reasoning should have provenance, not just content.
```

## The Fresh Signal

On October 12, 2026, Anthropic published [new research on defenses against model distillation](https://www.anthropic.com/research/distillation-defenses). The company says attackers had moved protected reasoning between conversations, models, and accounts while using large networks of fraudulent accounts to keep trying different extraction methods.

Anthropic reports that its newer controls reduced the amount of reasoning data harvested on its platform by roughly 90% to 99%. It also says the result is early evidence, that the defenses remain a cat-and-mouse game, and that they have not yet faced every possible sophisticated attack.

The headline is about distillation.

The architectural lesson is broader.

Anthropic's [preserved thinking documentation](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking) describes reasoning blocks that are checked against three kinds of provenance:

- which conversation prefix produced the block
- which models are allowed to read it
- which organization or linked account produced it

If one of those conditions no longer holds, the API can reject or drop the block before the model reads it.

That turns reasoning from portable text into context-bound state.

## Content And Provenance Answer Different Questions

The content of a block answers:

```txt
What bytes are here?
```

Provenance answers:

```txt
Where did these bytes come from?
What history produced them?
Who is allowed to reuse them?
Which runtime understands them?
Has the surrounding context changed?
```

Two reasoning blocks can contain identical visible text while having different security meaning.

One may have been produced inside the current organization after a valid sequence of messages. The other may have been copied from another account, inserted into a modified conversation, or generated by a model with different protections.

String equality cannot tell those cases apart.

A signature or server-verifiable binding can.

This is familiar elsewhere in software. A session cookie is not accepted only because its text looks plausible. A signed webhook is checked against its origin and payload. A database transaction token belongs to a particular operation. An authorization capability has an issuer, scope, and lifetime.

Intermediate model state deserves the same seriousness.

## Bind The Block To The Conversation Prefix

A multi-turn AI request has a history:

```txt
system instructions
tools
user message
assistant response
tool result
next user message
```

Later reasoning is produced in the context of everything before it.

If an application changes an earlier system instruction, rewrites a tool result, removes a message, or inserts a new tool definition, the old reasoning no longer belongs to exactly the same conversation.

Anthropic's preserved-thinking design treats the `system` prompt, tool definitions, and messages before a reasoning block as its prefix. A block remains valid only while that prefix remains unchanged.

The practical data-structure rule is:

```txt
append new turns
do not silently rewrite old turns
```

This is not merely a vendor-specific inconvenience. It exposes a common flaw in AI application architecture: many clients regenerate history from templates on every request.

They may:

- insert the current date into the system prompt
- reconnect a tool and reorder the tool list
- shorten an old tool result
- re-encode an earlier image
- summarize part of the history locally
- rebuild the first message from changing project context
- remove an old reminder and add a revised one

The conversation may look equivalent to a human.

Cryptographically and behaviorally, it is not the same input.

## Append-Only Does Not Mean Infinite

An append-only conversation sounds incompatible with context limits.

Eventually, old turns must be compacted, summarized, or removed.

The solution is not to pretend no history changed. It is to make compaction an explicit state transition.

A secure compaction flow can look like this:

```txt
old signed prefix
    -> server-authorized compaction
    -> signed compacted checkpoint
    -> new append-only suffix
```

The checkpoint becomes the new trusted root for later turns. The system knows that the old history was intentionally replaced, which state survived, and where the new reasoning chain begins.

Without an explicit boundary, a client-side summary can accidentally combine:

- reasoning from the old history
- a rewritten version of that history
- new tool definitions
- new model behavior

The application then asks the model to continue as if nothing changed.

That is both a reliability problem and a security problem.

This connects to [Prompt Caching Is Part of AI Architecture](/blog/prompt-caching-is-part-of-ai-architecture). The same unstable prefixes that destroy cache reuse can also invalidate context-bound reasoning. Stable history is not only an optimization; it is part of session integrity.

## Model Binding Prevents Security Downgrades

Different models do not necessarily apply the same reasoning protections.

An application might begin a conversation with a stronger model, then route a later turn to a cheaper or faster model. A provider may also perform a fallback when the original model is unavailable.

If every model can read every reasoning block, a protected block can be handed to a weaker model and prompted for disclosure.

Model binding replaces that assumption with an explicit compatibility graph:

```txt
model A may read blocks from model B
model B may not read blocks from model A
```

The direction can matter. A newer or more protected model may safely consume state from an older model, while the reverse path is denied.

For developers, this means model routing is no longer only a quality and cost decision. It can also change which prior state remains readable.

A robust router should know:

- which model produced each reasoning block
- which candidate models may consume it
- whether fallback will drop protected state
- how the quality and cost change after a drop
- whether the user should be told that continuity was reduced

The wrong fallback can preserve availability while silently losing the reasoning needed for a difficult multi-turn task.

Availability is not the only invariant.

## Organization Binding Stops Cross-Account Reuse

Conversation and model binding still leave another route: copy a valid block into a request from a different account.

Organization binding closes that path by tying the block to the account or organization that produced it.

This is especially important when an AI platform has:

- customer-controlled API keys
- multiple cloud providers
- resellers and proxy services
- shared agent infrastructure
- tenant migrations
- test and production organizations

A block from tenant A should not become trusted context for tenant B merely because both tenants can call the same model.

Multi-tenant AI systems should therefore carry provenance through their own storage layer. A reasoning block record needs more than a blob:

```ts
type ReasoningState = {
  opaqueBlock: unknown
  conversationId: string
  tenantId: string
  producingModel: string
  createdAt: string
  sequence: number
}
```

The client should not inspect or modify the opaque block. The surrounding metadata lets the application prevent obvious cross-tenant and out-of-order mistakes before the API has to reject them.

This follows the same principle as [Opaque Tokens Must Stay Opaque](/blog/opaque-tokens-must-stay-opaque): client code should preserve a security-sensitive value without inventing meaning from its internal format.

## Dropping State Is Safer, But Not Free

When a reasoning block fails validation, an API has two broad choices:

1. Reject the request.
2. Drop the invalid block and continue without it.

Rejecting is loud and predictable. It forces the integration to fix its history handling.

Dropping is more available. The user still receives an answer, but the model may have to reconstruct work it could no longer read.

Anthropic's documentation reports that repeatedly dropping reasoning blocks can materially increase generated tokens, especially at higher reasoning effort. It can also change output quality on tasks where later turns depend on earlier analysis.

That creates a useful operational rule:

```txt
Drop is a recovery mode, not a healthy steady state.
```

If an integration chooses to continue after a mismatch, it should measure:

- how often blocks are dropped
- why they were dropped
- which client version sent the request
- additional output tokens and latency
- changes in task success
- whether the mismatch repeats on every later turn

A system that silently drops reasoning on every request may look functional while paying more for weaker continuity.

## Mismatches Need Structured Telemetry

Security transformations should not disappear inside a successful HTTP response.

Anthropic exposes an `input_transformations` array that can identify reasons such as:

```txt
prefix_binding_mismatch
model_binding_mismatch
organization_binding_mismatch
```

That is a good API pattern.

The application can distinguish:

- malformed input
- a conversation-history bug
- an intentional model switch
- a cross-organization violation
- a provider-side fallback

Without structured reasons, all of these become "the model forgot something."

Teams should turn the telemetry into product and operational signals:

- alert when prefix mismatches rise after a release
- record model-binding drops during routing
- treat organization mismatches as security events
- show continuity warnings for user-visible sessions
- compare mismatch rates by SDK and client version
- block retries that resend the same invalid body forever

An AI application cannot debug context integrity using only the final answer.

## A Signature Does Not Prove The Reasoning Is Correct

Provenance controls have a narrow job.

They can establish that a block came from an allowed model, within an expected conversation history, under an authorized organization.

They do not establish that:

- the reasoning is factually correct
- the reasoning faithfully explains the model's output
- every internal computation is represented
- the final answer follows logically from the visible text
- the model was not misled by bad context
- the action produced from the reasoning is safe

This distinction is essential.

Signed reasoning is authenticated state, not a formal proof.

For mathematical claims, machine-checkable proof remains a stronger standard, as discussed in [AI-Generated Mathematics Needs Machine-Checkable Proofs](/blog/ai-generated-mathematics-needs-machine-checkable-proofs). For real-world actions, policy checks and typed effects still need to run outside the model.

Provenance answers "does this state belong here?"

Verification answers "is this conclusion correct?"

Authorization answers "may the system act on it?"

Those are three different questions.

## A Practical Integration Checklist

For developers building multi-turn AI applications:

- Store assistant content blocks exactly as returned.
- Treat reasoning and redacted-reasoning blocks as opaque.
- Keep system instructions and tool definitions stable within a session.
- Append messages instead of rebuilding earlier turns.
- Give compaction an explicit, provider-supported checkpoint.
- Record the model and tenant that produced protected state.
- Define which model switches preserve reasoning continuity.
- Handle provider fallback as a state transition, not only a retry.
- Choose reject or drop behavior deliberately.
- Log every input transformation and its reason.
- Alert on repeated prefix mismatches.
- Treat organization mismatches as potential isolation failures.
- Measure cost, latency, and quality after dropped state.
- Never treat a valid signature as evidence that the reasoning is true.

The important implementation shift is small:

```txt
Do not store reasoning as reusable prose.
Store it as context-bound protocol state.
```

## Reasoning Needs A Home

AI systems are becoming more stateful.

They reason across turns, call tools, compact history, switch models, recover from failures, and continue work over long sessions.

As that happens, intermediate state cannot remain an unowned pile of text blocks that applications freely copy and rearrange.

Some state should travel.

Some state should expire.

Some state should survive only inside one tenant.

Some state should become unreadable after its history changes.

That is not a limitation of intelligent systems.

It is what mature protocol design looks like.

Reasoning can be useful without being universally portable.

Give it a conversation.

Give it a model boundary.

Give it an organization.

And when it no longer belongs, fail clearly instead of pretending the context is unchanged.
