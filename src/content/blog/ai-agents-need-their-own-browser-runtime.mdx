# AI Agents Need Their Own Browser Runtime

An AI agent can call an API when a service offers one. But the web is not a tidy collection of APIs. Important work still happens behind pages: compare a booking, read a dashboard, fill a form, or check a status that only appears after JavaScript runs.

That means agents need a browser. The obvious answer has been to give them a headless Chrome session and let the model click around. Cloudflare's newly open-sourced **Kitesurf** explores a different shape: a browser engine that runs on Workers, without a conventional browser container, and speaks the Chrome DevTools Protocol so familiar clients such as Puppeteer can connect.

The project is experimental, and it is not a drop-in replacement for every browser task. The more interesting idea is architectural: browser automation for agents may become a piece of isolated, scalable infrastructure rather than a hidden process attached to an app server.

![A model sends browser actions to an isolated runtime, which visits an untrusted website and returns structured results](/blog/ai-agents-need-their-own-browser-runtime-social.png)

## Why Give Agents A Separate Browser?

A normal browser is built for a person sitting in front of it. It keeps tabs and state, renders a broad set of web standards, and may carry cookies and logged-in sessions for a long time. An agent worker has different needs: short-lived tasks, parallel page visits, a way to inspect what happened, and a boundary between the agent and the code it visits.

Running a full browser for every task can be operationally heavy. A browser engine built for a serverless runtime aims to make sessions easier to create on demand and isolate from one another. In Kitesurf's case, the page engine parses HTML, applies CSS, runs JavaScript, and can render screenshots on Cloudflare Workers. It exposes CDP, the protocol that browser automation tools already know how to speak.

That separation matters. The language model decides what to try; the browser executes a page; the agent harness decides which actions are allowed and what information returns to the model. Those are different jobs, and combining them into one privileged process makes failures harder to contain.

## What Kitesurf Actually Changes

Kitesurf is not just a wrapper around a remote Chrome binary. Its repository separates the browser session engine, page scripting, and page rendering. It also builds on open-source Rust projects compiled to WebAssembly for pieces such as parsing, layout, and painting. For page JavaScript, it can use isolated Dynamic Workers and includes a WebAssembly JavaScript engine as a fallback.

Because it supports CDP, existing tools can connect to it. A developer can run it locally, connect Puppeteer, or point an AI harness at the CDP endpoint. Cloudflare has released the code under Apache 2.0, so developers can inspect, modify, and deploy their own instance.

The practical question is not simply “Is this faster than Chrome?” Cloudflare describes its goal as using less CPU and memory than a full Chromium browser, but this is an experimental project whose compatibility and performance are still being improved. Before choosing it, a team should test the sites and flows it actually needs, including rendering, JavaScript, downloads, authentication, and failure recovery.

## A Browser Is Also An Authority Boundary

The browser is where an agent meets untrusted content. A page can contain instructions aimed at the model, misleading buttons, hostile downloads, or code that tries to reach unexpected network destinations. The agent may also be operating with cookies, account access, or permission to submit forms.

An isolated page runtime can help separate page execution from the host process. But isolation is not a complete security policy. The service still needs explicit rules for which domains it can visit, which requests it can make, how credentials are supplied, what data is returned to the model, and whether a human must approve a consequential action.

There is a particularly important deployment detail: Cloudflare's documentation says a deployed Kitesurf endpoint is public by default and does not include built-in authentication. It recommends protecting the endpoint with Cloudflare Access or another authentication layer. The docs also say that deploying Kitesurf on Cloudflare requires a paid Workers plan because it uses Dynamic Workers to isolate pages.

That is a useful reminder for any agent browser: a CDP endpoint is powerful. Anyone who can reach it may be able to drive the browser, inspect pages, or consume the account's resources. Treat the endpoint like a privileged service, not like a harmless preview URL.

## What It Does Not Solve

Kitesurf does not make agent browsing inherently safe, and it does not mean every website will behave exactly as it does in Chrome. The project is still improving web standards support, rendering fidelity, and performance. A lightweight engine may be the right tradeoff for many automation tasks and the wrong choice for pages that depend on browser features it does not yet match.

It also does not solve the permission problem. A browser can faithfully click “Submit”; it cannot determine whether the user intended to submit that particular form unless the surrounding system has a trustworthy way to establish intent. An agent needs scoped credentials, per-action confirmation for sensitive operations, and a record of what it did.

For related design questions, see [why MCP servers should start only when needed](/blog/mcp-servers-should-start-on-demand), [why agent permissions need receipts](/blog/personal-ai-agents-need-permission-receipts), and [why robots.txt is too blunt for AI agents](/blog/robots-txt-is-too-blunt-for-ai-agents). A browser runtime is another layer in that system, not a replacement for permission design or web standards.

## The Bigger Shift

The web is slowly acquiring an automation layer. It will not be made of one agent protocol or one browser engine. It will be a stack: a model, a harness, tools, a browser runtime, identity and access controls, and websites that may or may not be designed for machine interaction.

Open-sourcing Kitesurf makes one part of that stack easier to examine and adapt. The next evidence to watch is practical: compatibility tests, security boundaries, performance on real workloads, and whether developers can operate it without leaving a powerful browser endpoint exposed.

Agents do not just need a way to click the web. They need a place to do it that can be isolated, inspected, limited, and shut down when the task ends.
