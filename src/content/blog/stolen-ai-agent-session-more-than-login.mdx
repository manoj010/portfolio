# A Stolen AI Agent Session Is More Than A Stolen Login

A stolen login is bad.

A stolen AI agent session can be worse.

The difference is not that AI credentials are magical.

It is that an agent is designed to connect things.

It may read messages, search files, remember preferences, control a browser, call APIs, inspect a device, and act across several services on the user's behalf.

That makes the session more than proof that somebody logged in.

It can become a portable bundle of delegated authority.

```txt
one stolen session
does not always expose one account

it may expose every capability connected behind the agent
```

This is the security problem teams need to design for now.

## The Fresh Signal

On September 22, security researcher Patrick Wardle published [not-a-mused](https://github.com/pwardle/not-a-mused), a proof of concept targeting the macOS app for Meta's Muse assistant.

The issue involved an undocumented configuration setting used by the app for its dictation endpoint. According to the research, another unprivileged process running as the same macOS user could change that setting, redirect traffic to an attacker-controlled endpoint, capture prompts or audio, inject prompts, and obtain authentication material associated with the session.

[VentureBeat reported](https://venturebeat.com/security/meta-patched-muses-zero-day-but-security-teams-still-lack-visibility-into-what-the-agent-can-access) that Wardle demonstrated access to capabilities the user had connected to the assistant, including a linked phone's location and Bluetooth scanning. Meta reportedly deployed a hotfix within a day.

The limits of the finding matter.

This was not described as a remote exploit that could silently compromise a clean machine from anywhere on the internet. It required an attacker to already have code executing locally as the user. The research also did not show that Muse's cloud isolation had been defeated.

That makes the lesson more precise, not less important:

```txt
local compromise was the entry point
the agent session amplified what that compromise could reach
```

## An Agent Session Is An Authority Multiplier

Traditional applications often have a narrow job.

A notes app accesses notes.

A calendar app accesses calendars.

A mail client accesses email.

An agent tries to coordinate all three.

That is the product value.

It is also the security concentration.

Imagine an assistant connected to:

- email
- calendar
- cloud storage
- source repositories
- a browser session
- a phone
- smart home controls
- company tools
- payment or booking services

If every connection is available through one reusable agent session, stealing that session does not merely impersonate the user inside one interface.

It may inherit the agent's reach.

This is similar to stealing a cloud administrator token, except the authority may be spread across consumer devices, enterprise services, and physical actions at the same time.

The risk is not created by the model alone.

It is created by the combination of:

```txt
model capability
+ connected tools
+ delegated permissions
+ session credentials
+ weak containment
```

## The Login Screen Is Not The Security Boundary

Teams often put their strongest authentication at sign-in:

- password
- passkey
- multi-factor authentication
- device approval
- identity-provider policy

Those controls are valuable.

But after login, many systems issue a bearer token.

Whoever possesses the token can use it.

The server may not know whether requests are coming from the legitimate app, injected code, copied browser storage, malware running under the user's account, or another process that found the credential.

For ordinary software, this is already dangerous.

For agents, it becomes an ambient-authority problem.

The token may silently carry permission to invoke many tools without forcing each one to prove who is acting, why the action is needed, or whether the user still approves.

Authentication answers:

```txt
who established this session?
```

Agent authorization must also answer:

```txt
which capability is being used?
for what task?
against which resource?
for how long?
with what user approval?
```

## A Prompt Cannot Contain A Stolen Session

It is tempting to give the assistant a rule such as:

```txt
Only use connected services for the user's legitimate requests.
```

That is useful behavior guidance.

It is not a security boundary.

An attacker who has the credential may call the underlying service without following the intended conversational path. An injected request may look legitimate to the model. A compromised client may alter configuration before the model sees anything.

As I argued in [Agent Rules Should Live Outside the Prompt](/blog/agent-rules-should-live-outside-the-prompt), enforceable policy belongs in infrastructure the model cannot rewrite.

The system should remain safe even when:

- the model is confused
- the client is modified
- a prompt is malicious
- local code is hostile
- one connector is compromised
- a session token leaks

That is what makes a control a boundary.

## Treat Each Tool As A Separate Capability

The agent should not receive one giant credential that unlocks everything.

Use separate, narrow capabilities.

For example:

```txt
calendar.read        expires in 15 minutes
email.draft          limited to one thread
email.send           requires step-up approval
drive.read           limited to one folder
device.location      one request, foreground only
purchase.confirm     amount and merchant bound
```

This changes the failure mode.

If the calendar-read capability leaks, the attacker should not automatically gain email-send or device-location access.

If a phone connector is compromised, it should not expose the user's cloud drive.

If a token is replayed from another machine, sender constraints should reject it.

This is the same reason [personal AI agents need permission receipts](/blog/personal-ai-agents-need-permission-receipts): users and operators need a visible, inspectable record of what authority exists.

## Better Agent Sessions Need Better Token Design

Agent credentials should be designed under the assumption that one will eventually leak.

Useful controls include:

### Short lifetimes

A token that lives for minutes has a smaller theft window than one that remains valid for weeks.

Long-running agents can refresh authority through a controlled service instead of carrying permanent credentials.

### Audience binding

A token created for the calendar connector should not be accepted by file storage, device control, or a generic agent API.

### Sender constraints

Where possible, bind the token to a device key, workload identity, or proof-of-possession mechanism. Copying the token alone should not be enough to replay it elsewhere.

### Task and resource scope

Permissions should describe the specific operation and resource, not a broad promise such as "access connected services."

### One-time capabilities

Sensitive actions such as sending, deleting, purchasing, unlocking, or revealing location should use single-use authorization.

### Independent policy checks

The service executing the action should check policy outside the model and outside the client. It should be able to deny a technically valid token when context is wrong.

### Fast revocation

Users and administrators need one place to see every active agent session, connected service, device, permission, and recent action, then revoke any of them immediately.

## Local Configuration Is Security-Critical

The reported Muse issue also highlights an easy-to-miss surface: application configuration.

An endpoint override can look like harmless developer convenience.

But if it controls where authenticated traffic is sent, it is part of the trust chain.

Security-sensitive configuration should be:

- unavailable in production builds unless explicitly required
- validated against a strict allowlist
- protected from modification by unrelated processes
- ignored when supplied through unsafe user defaults or environment variables
- logged when changed
- covered by tamper detection where appropriate

The same applies to proxy settings, plugin directories, tool manifests, certificate choices, browser-debug ports, and local callback URLs.

Anything that can redirect authenticated agent traffic deserves the same scrutiny as the credential itself.

## Step-Up Approval Must Be Bound To The Action

Asking the user "Are you sure?" is not enough.

Approval should state exactly what will happen:

```txt
Share report.pdf
with finance@example.com
using your work email
now
```

The resulting authorization should be cryptographically or server-side bound to that action.

It should not become a fresh general-purpose session.

For higher-risk capabilities, approval may also require:

- biometric confirmation
- a trusted device
- a second channel
- a transaction limit
- a waiting period
- enterprise policy approval

This creates friction where friction is useful.

## Visibility Is Part Of Containment

Companies cannot respond to an agent-session incident if they cannot see the session.

Security teams need logs that answer:

- Which agent identity acted?
- Which human delegated the authority?
- Which model or runtime initiated the request?
- Which tool was invoked?
- Which resource was touched?
- Which device and process held the session?
- Was the action approved, denied, or modified?
- What other services could the same credential reach?

The last question is critical.

Incident response needs a map of the credential's potential blast radius, not only a list of actions already observed.

Unusual patterns should trigger containment:

- a token appearing on a new device
- location requests immediately after configuration changes
- tool calls unrelated to the active task
- many connectors invoked in quick succession
- repeated approval failures
- access at unusual times
- a session suddenly behaving like automation rather than a person

## Design For The Compromised-Agent Case

Agent security cannot stop at preventing compromise.

It also has to limit compromise.

That means asking during design:

```txt
If this exact session is stolen right now,
what is the maximum it can read, change, send, spend, or control?
```

Then reduce the answer.

This is the same blast-radius principle used for [AI safety tests](/blog/ai-safety-tests-need-blast-radius-limits), applied to everyday agent sessions.

Do not give the session more reach than the current task requires.

Do not make permissions live longer than the task.

Do not let one connector silently authorize another.

Do not let the model approve its own escalation.

Do not assume a locally authenticated user means every local process is trustworthy.

## The Bigger Lesson

AI assistants are becoming useful because they can cross application boundaries.

Security has to cross those boundaries too.

The right mental model is not:

```txt
an AI app with a login
```

It is:

```txt
a delegated identity system
that happens to use an AI model
```

That system needs least privilege, scoped capabilities, trustworthy configuration, independent policy enforcement, strong revocation, clear audit trails, and a blast radius designed for failure.

The recent desktop-app finding was patched quickly, and its local prerequisite should not be exaggerated.

But it revealed the shape of a problem that will keep returning.

When an agent sits between a person and many services, its session becomes a high-value security boundary.

Protecting the login is only the beginning.
