# Running Local LLMs Efficiently: Quantization, Ollama, and LM Studio

A year ago, running a capable language model locally usually meant expensive hardware, a complicated setup, or both.

That is no longer the whole story.

Quantization, efficient inference engines, and tools such as Ollama and LM Studio have made local AI practical on ordinary laptops and desktops. The result may not replace a frontier cloud model for every task, but it can be private, fast, inexpensive to reuse, and surprisingly capable.

After experimenting with smaller models, larger quantized models, and agent systems such as Hermes Agent, OpenClaw, and Odysseus, one lesson keeps returning:

```text
You do not always need the biggest model.
You need the right model running efficiently.
```

![A consumer workstation running a quantized language model locally](/blog/local-llms-quantized-social.png)

---

## Why Run an LLM Locally?

Local inference gives you a different set of trade-offs from a hosted API.

### Privacy and control

Prompts, source code, notes, and documents can remain on your machine. That matters when you are working with personal information, internal documentation, or a codebase that should not leave your environment.

Local does not automatically mean secure, of course. Applications can still log conversations, extensions can still make network requests, and downloaded models should come from sources you trust. But local execution gives you much more control over the data path.

### Predictable cost

A cloud API charges for usage. A local model consumes hardware, electricity, and your time, but there is no additional token bill each time you run it.

That makes local inference attractive for repetitive workflows such as indexing notes, summarizing documents, experimenting with agents, or processing a large batch of non-sensitive text.

### Offline availability

Once the model is downloaded, it can work without an internet connection. This is useful while traveling, during unreliable connectivity, or inside isolated development environments.

### Freedom to experiment

You can switch models, change quantization levels, adjust context length, expose a local API, and connect the model to your own tools. Local AI turns the model into infrastructure you can inspect and shape.

## The Four Things That Determine Whether a Model Will Run Well

Before downloading a model, look at four constraints:

1. Model size and quantization.
2. Available RAM and VRAM.
3. Context length and KV-cache usage.
4. How much of the model can be accelerated by the GPU.

People often focus only on parameter count. That misses half the picture.

A smaller model with full GPU offload can feel much faster than a larger model split between GPU and system memory. A model that fits comfortably at an 8K context can become slow or run out of memory when pushed to 64K. The workload matters as much as the model name.

## Understanding Quantization

Model weights are commonly trained or distributed at relatively high precision, such as FP16 or BF16. A rough estimate for FP16 weights is:

```text
parameters x 2 bytes
```

So a 7-billion-parameter model needs roughly 14 GB for its weights alone. Inference also needs memory for runtime overhead, temporary buffers, and the KV cache used to remember the conversation.

Quantization stores weights with fewer bits. A 4-bit version can reduce the weight footprint dramatically, making a model possible to run on consumer hardware.

| Quantization | Memory use | Typical trade-off |
| --- | --- | --- |
| Q8 | High | Very close to higher-precision quality |
| Q6 | Moderately high | Excellent quality, less memory saved |
| Q5 | Moderate | Strong quality-to-memory balance |
| Q4 | Low | Usually the practical starting point |
| Q3 | Very low | More noticeable quality loss |
| Q2 | Extremely low | Large compromises; use only when necessary |

These labels are useful shorthand, not universal guarantees. Different quantization methods and model architectures can behave differently at the same nominal bit depth.

For most people, **Q4 or Q5 is the sensible place to begin**. Move upward when you have spare memory and quality matters more than speed. Move downward only when fitting the model is the main constraint.

---

## Memory Is More Than the Model File

The download size is not a promise that the model will fit comfortably.

You also need room for:

* The inference runtime.
* The operating system and other applications.
* The KV cache, which grows with context length.
* Temporary compute buffers.
* Vision components for multimodal models.

A useful rule is to leave headroom. If a model file nearly fills all available RAM or VRAM, the system may spill into slower memory, start paging, or fail when the conversation grows.

For example, an 8 GB model on a machine with 8 GB of total RAM is not an 8 GB setup. The operating system needs memory too.

---

## Context Length Has a Real Cost

Long context windows sound impressive, but every extra token has a memory and processing cost.

The model's KV cache stores information from previous tokens so they do not have to be recomputed from scratch. As context grows:

* Memory consumption rises.
* Prompt processing takes longer.
* Time to the first generated token increases.
* Irrelevant material can distract the model.

Do not set the maximum context just because the model supports it. Start with the smallest context that comfortably fits the task, then increase it when the workload actually needs more history.

Good retrieval and selective context often beat dumping an entire repository or document archive into one prompt.

## Ollama or LM Studio?

Both tools make local inference approachable, but they suit different working styles.

### Ollama: simple automation and developer workflows

Ollama is a natural fit when you want a command-line workflow, a local API, repeatable model configuration, or integration with an agent framework.

Running a model can be as simple as:

```bash
ollama run qwen3:8b
```

Its strengths include:

* Straightforward model management.
* A clean CLI and local API.
* Easy integration with scripts and agents.
* Reusable model configuration through Modelfiles.
* A good developer experience for automation.

I tend to use Ollama when the model is part of a workflow rather than the entire product.

### LM Studio: visual discovery and tuning

LM Studio is often the fastest route for someone who wants to download a model, adjust loading options, watch memory use, and chat without living in a terminal.

Its strengths include:

* Visual model search and management.
* Clear loading and performance controls.
* An OpenAI-compatible local server.
* Runtime statistics that make comparison easier.
* A beginner-friendly desktop experience.

I like LM Studio for exploring model variants and seeing how changes to context, offload, and sampling affect the experience.

Neither tool is universally better. Ollama feels at home in scripts and agent stacks; LM Studio is excellent for interactive experimentation. They can also coexist on the same machine.

## Choosing a Model for Your Hardware

The best model is the one that fits with enough headroom to stay responsive.

### Rough starting points

| Model class | Good for | Hardware reality |
| --- | --- | --- |
| 3B-4B | Summarization, extraction, lightweight chat, simple tools | Runs on modest systems; quality varies by task |
| 7B-9B | Everyday chat, coding help, writing, local agents | The practical sweet spot for many users |
| 12B-14B | Better reasoning and writing consistency | Benefits greatly from more RAM or VRAM |
| 27B-32B | More demanding coding and reasoning | Often needs substantial memory or mixed CPU/GPU inference |
| 70B+ | High capability with the right model | Expensive and usually slow on typical consumer machines |

These are guidelines, not laws. Architecture, quantization, prompt length, and inference backend all affect performance.

My recent experiments have included 4-bit variants from the Qwen family through both Ollama and LM Studio. What surprised me was not that they could beat every cloud model. They cannot. It was how often a smaller model was already sufficient for coding assistance, documentation, research notes, blog drafting, and tool-driven workflows.

## A Practical Tuning Workflow

Randomly changing settings makes local inference feel mysterious. A small, repeatable benchmark makes it understandable.

### 1. Start with a Q4 model that fits comfortably

Choose a 7B-9B model if your hardware can accommodate it with headroom. Test it on the work you actually perform, not only on a generic chat prompt.

### 2. Use a realistic context length

Begin around the context your normal task requires. Do not begin at the model's advertised maximum.

### 3. Confirm where inference is running

Check whether the model is fully on the GPU, partially offloaded, or running on the CPU. In Ollama, `ollama ps` can help you inspect loaded models and their processing placement. LM Studio exposes loading and runtime information in its interface.

### 4. Measure the experience

Record:

* Time to first token.
* Generation speed in tokens per second.
* Peak RAM and VRAM use.
* Output quality on two or three repeatable prompts.
* Whether long conversations remain stable.

Tokens per second is useful, but it is not the whole score. A fast model that repeatedly produces unusable code is slower in practice than a slightly slower model that gets the task right.

### 5. Change one variable at a time

Compare Q4 with Q5, or 8K context with 16K context. Do not change the model, quantization, context, and sampler together, because you will not know what caused the difference.

## Getting Better Results from Smaller Models

Smaller models expose vague instructions quickly. This is not always a weakness; it can teach you where your request is underspecified.

### Give the model the context it needs

Instead of:

```text
Build me an API.
```

Try:

```text
Build a Laravel API for a budgeting application.

Requirements:
- PostgreSQL
- JWT authentication
- CRUD endpoints for expenses
- Monthly category reports

Return the route design first. Do not write implementation code yet.
```

The second prompt defines the stack, scope, and immediate output. The model has fewer gaps to fill with guesses.

### Break work into stages

Ask for the database design, review it, then ask for API routes, validation, implementation, and tests. Smaller models often perform much better when each step has a narrow goal and fresh, relevant context.

### Keep retrieval selective

For code and documentation, provide the files or excerpts needed for the current decision. More context is not automatically better context.

### Use sampling controls deliberately

Lower temperature tends to make output more stable and is often useful for extraction, structured output, and coding. Higher temperature can help brainstorming, but the best value depends on the model and task.

Treat settings such as `0.1-0.3` as a starting experiment, not a universal law.

## Local Agents Make Efficiency Even More Important

Agent systems can call tools, read files, execute commands, and repeat a model many times during one task. That changes the performance equation.

A model that feels acceptable for one chat response may feel painfully slow when an agent invokes it twenty times. For agents, a smaller, faster model with reliable tool use can be more valuable than a larger model with better prose.

Projects such as Hermes Agent, OpenClaw, and Odysseus show why local models are interesting beyond chat. They can become a private reasoning layer for scheduled jobs, development tools, and personal automation.

But local agents also deserve caution. Tool access creates real consequences. Use restricted permissions, review destructive actions, keep backups, and avoid assuming that local execution makes an agent automatically safe.

## Common Mistakes

### Downloading the largest model first

If it barely fits, the system may become slower than a smaller model that runs entirely on the GPU.

### Maximizing context by default

Large context consumes memory and increases prompt-processing time, even when most of the content is irrelevant.

### Comparing only model names

Compare the exact model, quantization, backend, context, and hardware. Otherwise the comparison is incomplete.

### Optimizing only for tokens per second

Measure whether the answer is useful, follows instructions, and succeeds on your real task.

### Ignoring system headroom

Leave memory for the operating system, your editor, browser, and any tools the model or agent needs to run.

## What Matters More Than Model Size

After experimenting with different local AI setups, I keep coming back to five factors:

1. The model fits the task.
2. The quantization fits the hardware.
3. The context contains the right information.
4. The workflow breaks work into clear steps.
5. Performance is measured on real use cases.

A well-configured 8B model with focused context can be more useful than a much larger model starved of memory and buried under irrelevant information.

The future of local AI is not only about fitting larger models onto smaller machines. It is about using the computation we already have more intelligently.

---

## Final Thoughts

Local LLMs have crossed an important threshold: they are genuinely useful for everyday work.

Ollama makes them easy to automate. LM Studio makes them easy to explore. Quantization makes them small enough to run on hardware many people already own.

If you are starting today:

* Begin with a Q4 model in the 7B-9B range.
* Leave memory headroom.
* Keep context no larger than the task needs.
* Confirm CPU and GPU placement.
* Benchmark your real workflow.
* Move to a larger model or higher quantization only when the results justify it.

The best local model is not the one with the most parameters.

It is the one you can run comfortably, understand clearly, and use repeatedly to get good work done.
